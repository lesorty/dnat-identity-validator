VDDPI: V eriﬁable Decentralized Data Processing
Infrastructure for Data Usage Control and
Conﬁdential Data Processing
Shota Tokuda , Shohei Kakei , Y oshiaki Shiraishi , Member , IEEE, and Shoichi Saito
Abstract—The utilization of personal data can create new in-
sights. On the other hand, data providers have concerns about
unauthorized acquisition and misuse of provided data. We propose
a decentralized data processing infrastructure, named VDDPI, that
enables data providers to verify data processing implemented by
data consumers. VDDPI manages information on data processing
apps using distributed ledger technology, and data providers can
obtain this information and check whether the provided data will
be disclosed or not before providing data. Furthermore, by run-
ning the app using trusted execution environments (TEEs), the
integrity of the app and the conﬁdentiality of the data provided are
ensured. Expanding beyond data processing veriﬁcation, VDDPI
provides decentralized data usage control, allowing continuous
control over the number of uses, location, date and time of use.
We evaluated whether VDDPI meets security requirements derived
from STRIDE and performed formal veriﬁcation using ProV erif.
In addition, we implemented a prototype using Intel SGX and
Hyperledger Fabric and compared its performance with related
work. The results of the performance evaluation conﬁrmed that
the data processing time was approximately equivalent to related
work.
Index Terms—Data utilization, data usage control, distributed
ledger technology, formal veriﬁcation, trusted execution environ-
ment (TEE).

Data sovereignty, a concept related to the ability of individuals
to control the use of their personal data for the purpose of
protecting their privacy, is receiving attention [8]. One method
of achieving data sovereignty is to utilize personal data stores
(PDSs) [9]. PDSs manage personal data by individuals them-
selves on their own devices and servers, thereby mitigating the
risk of privacy violations. However, when data consumers intend
to process data, they should perform the processing on their own
systems using their own algorithms. This data processing may
result in the unrestricted use of the provided data. In order for
data providers to be able to provide personal data without privacy
concerns in such a scenario, it is essential to have a mechanism
that allows them to establish trust with the data processor that
runs on the untrusted data consumers.
Audit-oriented frameworks have been studied as a means to
increase accountability in data usage by recording how data and
applications were used in an immutable and transparent man-
ner. Nascimento et al. [10] proposed DNA T, which integrates
Ethereum and Intel SGX to provide publicly auditable usage
records. In DNA T, data and application providers can register
assets on a blockchain, and trusted nodes mediate access requests
to ensure that usage agreements are properly recorded.
Beyond audit-oriented frameworks, usage control has been
studied as an approach that provides stronger guarantees by tech-
nically enforcing conditions before and during data usage. Park
et al. [11] introduced data usage control to continuously monitor
digital resources in dynamic distributed environments. It extends
general access control by enabling more detailed data control
after data are provided. Recent research has been conducted
on methods to enforce compliance with data usage control in
distributed environments [12], [13], [14]. This research uses
a trusted execution environment (TEE) to achieve compliance
with usage conditions through data usage control. Some work
checks data processing code to prevent data misuse [15], [16],
[17], [18]. However, this veriﬁcation relies on assumptions or
a single point of failure, risking misuse if the central authority
is compromised. Another approach involves releasing the code
for veriﬁcation by data providers [19], [20], [21], but companies
are unwilling to disclose the code due to its intellectual property
rights [22]. Thus, it has been considered that it is difﬁcult for
data providers to properly verify programs implemented by data
consumers running in a remote TEE enclave [23].

The processing infrastructure that handles sensitive data such
as personal data behaves as a trusted system, so it should be
secure and dependable, and should guarantee the following prop-
erties: conﬁdentiality, integrity, reliability, and maintainability
and more [24]. By realizing such a secure data infrastructure,
concerns about the conﬁdentiality of provided data can be elim-
inated, thereby promoting the utilization of personal data.
This paper introduces a veriﬁable decentralized data process-
ing infrastructure, VDDPI, using TEE and distributed ledger
technology (DLT). This infrastructure uses TEE to ensure the
security of provided data and data processing processes, and
guarantees dependability using blockchain technology. VDDPI
addresses security requirements in a decentralized data process-
ing model assumed in this study to counter threats identiﬁed
in STRIDE. Data consumers implement data processing codes
based on a template speciﬁed by VDDPI. This template contains
codes for communication with data providers and data usage
control, and the security baseline for data processing is assured
by verifying that the implemented source code is compliant with
the template. In addition, data ﬂow analysis is performed to
prevent unindended data leakage. VDDPI uses smart contracts
to ensure the integrity of the veriﬁcation and analysis process.
VDDPI enables data providers to verify enclave programs run-
ning in remote TEE enclaves, combining ﬂexible data processing
with data protection.
We previously proposed a data usage control method in a
decentralized data processing model [25]. However, various
threats exist in the actual operation of the system. Therefore, in
this paper, we propose a data processing infrastructure based on
our method that mitigates these threats. In addition, we conduct
a more rigorous security and performance evaluation of VDDPI.

II. B ACKGROUND
A data utilization model involves data providers depositing
data with a central authority, such as a broker, allowing data
consumers to gain insights. This centralized data processing
model is the dominant model for online services today, where a
single organization collects and stores information on multiple
individuals [26]. This model forces data providers to trust that
the central authority will not misuse their data. If this central
authority is compromised, the data could be misused. As a
data infrastructure develops, increasing data types and volumes
heighten leakage risks, creating a dilemma [27]. This dilemma
requires a choice: accept the risk to scale services or limit data
to reduce risk. A decentralized approach mitigates this risk by
enabling direct data exchange between providers and consumers.
In a model where data providers and consumers communicate
directly, it is important to protect the provided data in-use,
at-rest, and in-transit. TEE can help archieve this protection,
but unauthorized processing by untrusted data consumers may
compromise provided data. Several studies have proposed sys-
tems to verify data processing in TEE enclaves [15], [16], [17],
[19], [20], [21]. However, as the size of code increases, the
veriﬁcation by data providers or third parties becomes infea-
sible [23]. Furthermore, data consumers may require the ability
to implement processing beyond predeﬁned code [28].I ti s
therefore necessary to incorporate a mechanism to mechanically
verify the data processing implemented by data consumers. In
addition, continuous control of provided data is important for
data protection in a decentralized data processing model. In
a decentralized data processing model where data consumers
cannot be trusted, technical assurance of continuous data control
is important. However, research on dependable guarantees for
data sovereingty remains limited [29].
A. Motivating Use Case
We assume that individuals manage their data and provide
data as needed and develops a generic infrastructure that can be
applied to various cases. However, we focus on a speciﬁc use
case in this paper. Fig. 1 shows a hypothetical use case in which
data collected from personal smartphones is utilized to support
evacuation guidance in the event of a disaster within a facility.
In normal times, a facility as a data consumer can request and
store personal data from PDSs via data processor in the cloud
environment. While the facility calculates evacuation routes
based on real-time damage assessments, uniform instructions
may not be suitable for all visitors - such as wheelchair users
who cannot use staircases. Furthermore, if health conditions,
age, or other personal attributes are recorded in advance, ﬁrst
responders can leverage this information to assist in lifesaving
activities. In addition, the use of location information obtained
from smartphones enables rapid lifesaving activities. From a

B. Assumed Data Processing Model
We deﬁne a decentralized data processing model as one in
which data consumers execute data processing on their own
systems, and we adopt this model for the data processing as-
sumed in this study. The data processing model assumed in
this study is shown in Fig. 2. The data processor in this model
may be running in the data consumer’s local environment, or
it may be running in the cloud environment used by the data
consumer. In this model, it is assumed that the data consumer
implements the data processing and the data consumer can
temporarily store the provided data for ﬂexibility in data use.
This temporary storage enables data processing even when the
data consumer cannot establish communication with the data
provider.
In this model, data providers need to send data to untrusted
data consumers directly. It is therefore essential to implement
a continuous control mechanism to prevent the misuse of the
provided data. The use of TEEs is gaining attention as a way
to technically ensure continuous control [29]. Speciﬁcally, data
providers provide data consumers with data usage policies that
include usage conditions. This policy is stored with the provided
data in order to enforce it when the data is reused.
C. Trusted Execution Environment
It is important to ensure data conﬁdentiality during data use
when processing sensitive data in a cloud environment or an
external environment. One way to ensure the conﬁdentiality of
data during processing is a trusted execution environment (TEE).
It ensures the authenticity of the enclave code, the integrity of the
runtime states, and the conﬁdentiality of its code and data [30].
In this study, we opted for Intel Software Guard Extensions
(SGX) [31] as a TEE. SGX creates an encrypted protected
area in memory called enclaves. Applications running within
an enclave can be uniquely identiﬁed by MRENCLA VE, a hash
value that depends on the enclave program and conﬁguration
ﬁles. SGX also has a sealing mechanism that stores conﬁden-
tial data in non-volatile memory encrypted with an enclave
program-speciﬁc key [32]. This mechanism enables data reuse
with conﬁdentiality.
Remote attestation is used to attest the legitimacy and in-
tegrity of an enclave program and platform by presenting an
attestation report, including MRENCLA VE, to remote entities.
By checking MRENCLA VE, remote entities can verify that the
program in an enclave with which they communicate is their
intended program. RA-TLS [33] is a method for embedding
remote attestation in a TLS negotiation.
D. Distributed Ledger Technology
It is important to guarantee data integrity when sharing data.
Distributed ledger technology (DLT) is a method of ensuring
integrity by storing data across multiple distributed nodes. DLT
allows multiple participants to maintain synchronized ledgers
on a network without a central administrator. This technology
guarantees transaction transparency and data integrity. In this
research, we opted for Hyperledger Fabric [34], permissioned
DLT. Permissionless DLT is open to anyone, and each participant
is anonymous, whereas permissioned DLT consists of partici-
pants approved by an administrator.

A. Assumptions and Limitations
In this study, we assume that adversaries do not perform
side-channel attacks against vulnerabilities in TEE. We also
assume that the cryptographic primitives used in TLS and X.509
certiﬁcates are not compromised and are sufﬁciently secure.
Additionally, we assume that private keys are not compromised.
This study does not cover the conﬁdentiality of processing
results after they are obtained by the data consumer.
In addition, our design assumes that the data processing code
is written in a restricted form so that the registry’s veriﬁcation
process can inspect the code and apply static taint analysis.
In particular, the code is expected to follow the template and
programming constraints imposed by VDDPI, and leakage pre-
vention relies on allowlisted functions such as sanitizer functions
and other permitted operations. We therefore assume that al-
lowlisted functions are correctly implemented for their intended
purpose and that the allowlisting procedure, including manual
review, is conducted appropriately. Due to these constraints,
VDDPI supports existing data processing apps only to the
extent that they can be adapted to our template and program-
ming restrictions; consequently, porting legacy applications may
require refactoring or partial reimplementation to meet these
restrictions. Moreover, because the veriﬁcation process needs
sufﬁcient visibility into the processing program to check policy
compliance and potential leakage, the conﬁdentiality of the
processing code is only partially preserved; therefore, scenarios
that require keeping the full processing code strictly secret from
external parties are not supported in the current design.
We also rely on components outside the enclave trust bound-
ary to operate as intended. Speciﬁcally, we assume that the per-
missioned distributed ledger platform, the certiﬁcate authority
for authentication, and the software toolchain used to build and
analyze the processing code are not compromised in a way that
breaks the integrity of veriﬁcation or the correctness of access
control. While some nodes may be faulty or compromised, we
assume that a data processor can mitigate this risk by consulting
multiple registry nodes and by validating ledger records through
the platform’s consensus mechanism. We do not address attacks
that fundamentally undermine these external trust assumptions
(e.g., compromises that subvert consensus or the integrity of the
toolchain).
Finally, our design provides only limited protection against
state rollback and certain classes of memory attacks. Although
sealing enables reuse of conﬁdential state, it does not inher-
ently prevent an adversary from rolling back sealed data to
a previous version; thus, strong rollback protection requires
additional platform support (e.g., trusted monotonic counters) or
is treated as a limitation. Furthermore, beyond the side-channel
attacks excluded above, we do not guarantee conﬁdentiality if
vulnerabilities in the TEE implementation or privileged software
enable direct disclosure of enclave memory; such attacks are
considered out of scope and remain a limitation of the protection
offered by this study.
B. Assumed Adversaries
As discussed in Section II, decentralized data processing
models may lead to reluctance to share data because of losing
control over provided data. This is because data providers are
concerned that untrustworthy data consumers may fraudulently
obtain or misuse the data provided. Therefore, this study designs
an infrastructure that addresses these concerns. Speciﬁcally, we
assume the following ﬁve types of attacks.
r UA-1: Unauthorized acquisition of provided data
r UA-2: Unauthorized acquisition of processing results
r UU-1: Failure to comply with data usage policies
r UU-2: Data use by unauthorized data consumers
r UU-3: Data use by unauthorized data processing app
UA-1 and UA-2 represent attacks related to the unauthorized
acquisition of data. These attacks result in the disclosure of data
to which the data provider does not consent. In UU-1, UU-2, and
UU-3, data consumers perform unauthorized use of provided
data without consideration of the terms agreed upon by data
providers at the time of its provision.
C. Stride
We use STRIDE[35] for threat analysis of the data processing
model assumed in this study. STRIDE is a threat modeling
methodology developed by Microsoft that can analyze six types
of threats (S
pooﬁng, Tampering, Repudiation, Information Dis-
closure, D enial of Service (DoS), and E levation of Privilege
(EoP)). In this paper, we employ STRIDE-per-Element [36],
which applies STRIDE to each element of a DFD, to perform
threat analysis.
D. Threat Modeling
First, to identify potential threats, we convert the assumed
data processing model to a DFD. The converted DFD is shown
in Fig. 3. The DFD consists of four types of elements (External
Entity, Process, Data Store, and Data Flow). A data provider
has a data provision server and a database that stores provided
data and communicates between these entities. In this study,
to analyze threats from data providers’ perspective, the data
provider and the data store are surrounded by a trusted boundary.
On the data consumer side, there is a data processing app and
a data store for provided data, and a data consumer obtains
processing results from the app. In addition, data are provided
in the communication between the app and the server.

E. Security Requirements
We deﬁne security requirements to prevent each of the attack
scenarios described in Section III-D. The security requirements
are shown in Table IV. As a result of the threat analysis, 12
security requirements were deﬁned to prevent the ﬁve types of
attacks in the assumed decentralized data processing model. Au-
thentication of apps and data consumers is necessary to prevent
spooﬁng (SR-1–3). Protection of data stores is also important to
prevent policy tampering and ensure conﬁdentiality of provided
data (SR-4, 5). In addition, the protection of communication

this requirement. It is also important to verify data processing
by the data provider, as apps may disclose provided data that
data providers do not intend (SR-12).

B. Processing Code Analysis
The proposed method employs data ﬂow analysis to follow
the ﬂow of provided data in data processing. However, it could
be difﬁcult to analyze accurately. Therefore, as described in
Section III-A, the method allows data consumers to implement
only the data processing code, restricting the use of system calls
and unauthorized third-party libraries that would complicate the
analysis. On the other hand, calls to functions included in the
allowlist are permitted. Then, data ﬂow analysis is performed
by static taint analysis while maintaining code brevity through
template compliance. It can be seen from the analysis that
the provided data will not be disclosed unless any part of the
provided data is returned from the data processing code.
The proposed method uses static taint analysis for data ﬂow
analysis of the data processing code within the code analysis
system shown in Fig. 4. Static taint analysis is a type of data
ﬂow analysis that traces data transitions within a program to
verify if data leaks have occurred. This analysis labels deﬁned
information sources, called taint source, and propagates the la-
bels among the variables. Then, when a labeled variable reaches
a deﬁned point, called taint sink, the data corresponding to that
label is found to be disclosed. In the taint analysis of the proposed
method, the arguments of the data processing code are set as taint
sources and the return value is set as a taint sink. By performing
taint analysis in such a setting, it is possible to check whether
provided data will be disclosed.
Provided data used as input in data processing affect the
processing results in some way. Even if some of the provided
data are modiﬁed, it is difﬁcult to determine the extent to
which such modiﬁcations result in anonymization. This data
ﬂow analysis prohibits the use of unauthorized third-party func-
tions and system calls, while allowing the use of authorized
functions. These authorized functions are intended to perform
anonymization, such as calculating averages, and act assanitizer

A. Data Model for Proposed Data Usage Control Method
This section outlines the information held by each entity
to realize the usage control proposed method described in
Section IV.F i g . 5 shows the relationship between the infor-

used to manage provided data and data processing code, and to
present requests and conditions. Data endpoint information to be
input into the data processing app is represented by a data usage

data to be used and how the data will be used. It is also used

B. Overview
Fig. 8 shows an overview of VDDPI. In this infrastructure,
data providers (DPs), data consumers (DCs), and a data process-
ing app registry (AR) exist as entities. In VDDPI, the data pro-
cessing app runs in a TEE enclave, ensuring the integrity of the
app and the conﬁdentiality of provided data during processing.
Furthermore, DCs send their source codes for the implemented
data processing code to the AR, and the analysis of the code uses
a smart contract in the permissioned DLT. This analysis could be
performed by the data provider; however, it would be an arduous
work. In addition, if the data provider performs the analysis,
the data consumer needs to provide the processing code to the
data provider, so the data consumer may be hesitant to share the
processing code and unable to analyze the code if the processing
code uses a highly conﬁdential algorithm. To address this, the
analysis in VDDPI is performed using permissioned DLT so that
the data processing code is not disclosed to anyone other than
the authorized entities that comprise the AR. In addition, smart
contracts ensure the integrity and fault tolerance of the analysis
process.
The data provision server obtains the PS using the ID of
the data processing app. To make the PS retrievable using the
app ID, it is necessary to link the processing app code to the
data processing app disclosure information with the app ID, and
record it in distributed ledgers. The app ID is calculated at the
build time. To match the ID recorded in the AR with the ID
of the app executed by the DC, the infrastructure employs the
same environment for app build system and DCs with container
technology. MRENCLA VE, used as the app ID, is a hash mea-
surement of the app. The AR calculates the app ID using its own
template. Therefore, if a DC modiﬁes the template, the app ID
will not match, allowing detection of tampering. Consequently,
VDDPI can ensure compliance with app templates by verifying
the app ID.
VDDPI enables the continuous control of provided data,
including temporary storage, by employing the data usage con-
trol method described in Section IV. In order to guarantee the
integrity of UPs and the conﬁdentiality of temporarily stored
data on the data consumer’s side, TEE sealing is employed for
the storage of data. When temporarily stored data is used, the
data processing is executed after unsealing provided data and
UP , and conﬁrming that the UP is satisﬁed. In order to achieve
continuous control of stored data in data processing apps, UPs
are managed in the form of a so-called sticky policy [39].
C. Two Types of Control Supported in VDDPI
In VDDPI, conditional control is implemented through event-
trigger-based control and usage-count-based control. For event
triggers, control is carried out using external trusted information
sources. In this paper, we support location- and time-based
control. For usage-count-based control, the remaining number
of allowed uses is recorded in sealed data, and control is enforced
based on this information. Since sealed data is tamper-resistant
and the integrity of decrement processing is guaranteed by a
TEE, it is ensured that the number of uses does not exceed the
limit speciﬁed by the data provider. The extension of controllable
conditions is discussed in Section IX.

processing is performed only when the usage conditions are
satisﬁed. The results were output outside the enclave. Finally,

the cached data are available, the data processing app retrieves
from the stored data and the UP . The stored data and the UP
are encrypted using TEE sealing so that stored data cannot be
obtained outside the enclave or from other enclave apps.

ECURITY EVA L U AT I O N
A. Requirements V eriﬁcation
In this section, we evaluate that VDDPI meets the security
requirements described in Section III-E.

VDDPI uses remote attestation between the data provision
server and the app to authenticate the app when data are pro-
vided. This remote attestation is TLS-based (RA-TLS), and data
providers can verify data consumers by verifying the X.509 cer-
tiﬁcate on the server during client authentication. Additionally,
by verifying the app’s input and output using the PS obtained
from the AR, the DP can be conﬁdent in the conﬁdentiality
of the provided data. However, an attacker could compromise
some nodes and replace the PS with a malicious one, potentially
misleading the DP into believing the app’s conﬁdentiality is
ensured. Against this attack, the DP can correctly perform app
authentication, including processing speciﬁcations, by compar-
ing responses from multiple AR nodes. These authentication
satisfy SR-1 and SR-2. In addition, the data processing app
employs TLS client authentication for data consumer authen-
tication, which satisﬁes SR-3.
VDDPI uses TEE sealing to encrypt and store provided data
and data usage policies on the data consumer side. As VDDPI
performs TEE sealing based on MRENCLA VE, the sealed ﬁles
can only be accessed by the enclave application that carried out
the sealing. Therefore, SR-5, and SR-7 are fulﬁlled by the use
of TEE sealing. SR-4, however, is only partially satisﬁed by this
mechanism, as there remains a risk that the provided data could
be rolled back. VDDPI cannot prevent such attacks, as described
in Section III-A. Nevertheless, existing studies have leveraged
monotonic counters to counter rollback attacks [40], [41], and
VDDPI could also mitigate this threat by incorporating a similar
mechanism.
The communication channels between the data provision
server and the data processing app and between the app and
the data consumer are encrypted as TLS is used. Thus, SR-6 and
SR-8 are satisﬁed because these channels are protected by this
encryption.
The data processing app runs within an enclave in VDDPI.
This protects the memory of the running app from tampering,
ensuring SR-9. Apps implemented by data consumers are veri-
ﬁed by a smart contract in the registry and linked to an app ID as
a PS. The data provision server veriﬁes that the app ID obtained
at remote attestation with the app matches the app ID of the PS
before providing data, guaranteeing that the app has been veriﬁed
with the smart contract. This guarantees that the app adheres to
the speciﬁed template and has not been tampered with. However,
data leakage remains possible if memory vulnerabilities in the
TEE are exploited, and VDDPI could be subject to such attacks,
as discussed in Section III-A. Consequently, SR-10 can only
be partially satisﬁed. Potential countermeasures include the use
of memory-safe programming languages and compiler-based
protections, but applying these measures to VDDPI is left as
future work. Moreover, apps that are implemented according
to the template adhere to data usage policies presented. These
policies are created by the data provision server based on the data
usage application, the data usage control mechanism in the app
guarantees compliance with the policies indicated in the US.
This enforcement of compliance with the template eliminates
any room for repudiation by data consumers, and this data usage
control mechanism satisﬁes SR-11. Finally, the veriﬁcation of
apps with a smart contract uses static taint analysis to verify
whether or not provided data are disclosed in data processing.
As mentioned earlier, the PS are guaranteed to be the app with
which the data provision server communicates by the integrity
of the TEE application and the information stored in distributed
ledgers, and by the authentication of the application via remote
attestation. Therefore, the data provider can obtain information
on data processing of the app before providing data, and SR-12
is satisﬁed.

VIII. R
ELA TEDWORK
In this section, we present related work such as data processing
using a TEE and DLT. TableVII shows the result of comparison
of related work. In addition to the used technology and the
assumed data type, the comparison focuses on data usage con-
trol, security of the data processing code, and ﬂexibility of data
processing. In the context of data usage control, we conducted
an analysis of the existence of a mechanism that complies with
the presented obligations and conditions, and the ability of data
providers to specify data processing. In addition, we examine the
ﬂexibility of data processing by evaluating the programmability
of the code and comparing the entities that implement data
processing. In data processing code security, we compare the
conﬁdentiality of the code itself and the entities by which the
data processing code is veriﬁed.
As a study focusing on the enforcement of obligations and
conditions in data usage control, OB-ABE[12] extends classical
attribute-based encryption (ABE) with enforceable obligations
using a TEE. OB-ABE allows data providers to deﬁne obli-
gations, thereby giving data providers ﬂexibility in controlling
provided data. Moreover, OB-ABE has been proven secure
through formal veriﬁcation by ProV erif. ReGov [13] is a de-
centralized data usage control architecture using TEE and DLT.
ReGov extends the existing Solid access control mechanism to
enable data usage control. DUCE[14] is a trusted and distributed
enforcement architecture using TEE and DLT to enforce usage
control policy. These studies have mechanisms to enforce obli-
gations and conditions for data usage control; however, they
have not performed the veriﬁcation of data processing at the
data destination.
As a study considering the veriﬁcation of data processing,
Regueiro et al. [15] proposed a privacy-enhancing distributed
protocol for data aggregation using blockchain and homomor-
phic encryption (HE). In this protocol, participants process a
query presented by a data consumer, and an operator represent-
ing the participants aggregates the results and returns them to the
data consumer. More et al. [19] proposed a private data market
architecture. This architecture allows ﬂexible access control
based on the policy system, and the computation system in
this architecture validates policies based on the attributes and
===== PAGE 14 =====
TOKUDA et al.: VDDPI: VERIFIABLE DECENTRALIZED DA TA PROCESSING INFRASTRUCTURE FOR DA TA USAGE CONTROL AND CONFIDENTIAL 6081
roles of the data buyer at the time of data purchase. b-DTC [20]
is a blockchain-based platform for decentralized trusted com-
puting. b-DTC performs computations off-chain, using TEE,
and records the performance and other information of the com-
putation as reputation on the blockchain via a smart contract.
Private Data Objects (PDOs) project [16] provides technology
for execution of off-chain smart contracts with conﬁdentiality
using SGX. PDOs, like VDDPI, focus on avoiding a single
point of failure. It is expected that the contract used for data
processing is shared ofﬂine in order to agree on its use prior
to use in PDOs. DNA T (Data aNd Application Tracking) [10]
proposes a platform for traceability by combining blockchain
and a TEE (Intel SGX) to record and track application ex-
ecutions and data usage in a tamper-resistant manner. When
the data is sensitive, DNA T assumes that pre-veriﬁcation has
been performed to ensure that the application is non-malicious,
performed by the data owner or by a trusted third party with
access to the source code. DNA T then executes the application
over the data inside an SGX enclave and releases the decryption
key only after attestation, ensuring that the pre-veriﬁed code
is executed without being tampered with. PrivacyGuard [17]
enables an individual’s control over the usage of private data
using TEE and blockchain. In PrivacyGuard, data usage contract
is recorded on the blockchain, data processing is performed in
off-chain contract execution environment provided by a TEE.
The data processing in PrivacyGuard is assumed to be ratiﬁed by
trusted sources in advance, and the veriﬁcation of data process-
ing is not performed in the system. These studies consider the
veriﬁcation of the data processing. However, it is assumed that
the veriﬁcation is conducted by data providers or trusted third
parties outside the framework. In addition, the conﬁdentiality of
the data processing code is compromised when the code is made
publicly available on data markets.
As a study that takes into account the veriﬁcation of the data
processing implemented by data consumers, TrustControl[18] is
a data usage control system focusing on protecting the sensitive
data and function code while preventing data misuse and leak-
age. Remote attestation in TrustControl is designed to enable
to verify the function codes implemented by data consumers.
However, this veriﬁcation is performed on a single attestation
server, thereby the server can be a single point of failure of
the veriﬁcation. MECT [47] is a SGX-based architecture for
trusted remote policy enforcement. In MECT, the data consumer
implements the app according to a predeﬁned template, and
the data provider’s server veriﬁes the code. As the number of
data providers increases, the cost of veriﬁcation is anticipated to
rise, given that each provider must verify the code. This differs
from VDDPI, in which analysis information is managed in the
data processing app registry, and the data provider acquires the
information from the registry.
As a study that considers both the enforcement of obligations
and conditions in data usage control and the veriﬁcation of data
processing, Lohmöller [21] proposed a federated data platform
architecture using TEE and DLT for reliable enforcement of
complex policies. This architecture uses TEE to guarantee the
enforcement of obligations and conditions for data usage control
when providing data to untrusted entities. Although this study
technically guarantees the enforcement of conditions for data
usage control and the control of data processing content, code
veriﬁcation is not performed mechanically. As a result, when
the size of code to be veriﬁed is considerable, it becomes
impractical to perform the veriﬁcation [23]. VDDPI can handle
such cases, as the smart contract veriﬁes data processing and
enables data providers to make data provision decisions based
on the app speciﬁcations. In addition, this veriﬁcation in VDDPI
is performed with permissioned DLT, and only data disclosure
information is disclosed to data providers. This approach par-
tially ensures the conﬁdentiality of the data processing code.
IX. D
ISCUSSION
A. Conﬁdentiality Challenges of Data Processing Code
As discussed in Section III-A, in VDDPI, the registry can
inspect the data processing code implemented by data con-
sumers. Because this registry is built on a permissioned DLT,
access is controlled rather than fully open. However, if the data
processing logic must remain conﬁdential, VDDPI is not an
appropriate choice. We therefore consider VDDPI suitable for
scenarios where conﬁdentiality is not required, such as general
route search algorithms.
For apps where the source code cannot be disclosed, applying
VDDPI remains challenging. To address this limitation, one
possible approach is to implement the data processing app to
perform dynamic taint analysis on its own execution and to run
only when the data usage policies are satisﬁed, thereby avoiding
the need to disclose the code. Nevertheless, this approach raises
concerns about increased execution time due to the overhead of
runtime taint tracking. These points remain challenges for the
future.
Another possible approach is to execute the AR-side work-
ﬂow, speciﬁcally the smart-contract-driven analysis and build
steps, inside an attested TEE environment, so that proprietary
processing code can remain conﬁdential even at registration
time. For instance, conﬁdential smart-contract frameworks such
as Hyperledger Fabric Private Chaincode (FPC) [48] execute
chaincode within Intel SGX enclaves, which can protect sen-
sitive inputs from peer operators. However, VDDPI’s registra-
tion workﬂow not only analyzes the submitted code but also
builds the data processing app and derives its app identiﬁer
(MRENCLA VE). Conducting this compilation inside such an
enclave is technically challenging and likely impractical in many
deployment settings, and therefore conﬁdentiality during com-
pilation remains an open issue. Moreover, extending TEE usage
to the registration toolchain introduces a bootstrapping issue:
the analysis and compilation components become part of the
trusted computing base and must be trusted for both correctness
and non-leakage.
B. Towards Flexible Data Usage Control
Data usage policy scope is an important requirement for data
usage control solutions [49]. VDDPI currently supports only
a limited set of basic conditions and cannot enforce controls
based on diverse conditions. In contrast, IDS deﬁnes 21 types

6082 IEEE TRANSACTIONS ON DEPENDABLE AND SECURE COMPUTING, VOL. 23, NO. 3, MA Y/JUNE 2026
of policy classes as policy templates for usage control [38], and
it is desirable for VDDPI to also support the implementation
of such policy classes. As a possible approach to realize this,
we are considering a method in which the registry manages
the control processes executed within data processing apps on
the distributed ledger it maintains. This would enable VDDPI
to achieve ﬂexible control and monitoring in accordance with
various data provision scenarios.
C. Challenges in Adapting Existing Applications to VDDPI
As described in Section III-A, adapting existing applications
to VDDPI involves several challenges. In conventional data
processing apps, numerous functions are typically invoked;
however, VDDPI imposes restrictions on function calls, which
prevents such applications from running as-is. Consequently,
while developing new applications from scratch would not pose
major difﬁculties, porting existing applications can be consid-
erably labor-intensive. In addition, data providers must deﬁne
appropriate data provision policies. These efforts can be sub-
stantial for applications with extensive dependencies or frequent
function calls, potentially leading to signiﬁcant redevelopment
costs.
Regarding the automation of adaptation, its feasibility would
depend on a mechanism capable of automatically converting
functions and system calls into those allowed by VDDPI. Nev-
ertheless, we consider this task to be challenging in practice.
D. Limitations of the Current Implementation
In the current implementation of VDDPI, we employ
Gramine-SGX and the CPython interpreter. Since both of these
components have a relatively large LoC, they broaden the po-
tential attack surface. In particular, Gramine-SGX may exhibit
unintended behavior due to vulnerabilities in its dependent li-
braries or exception handling, as suggested by the trends in its
security patches. Consequently, VDDPI can be also exposed to
such latent security risks. Implementing VDDPI with Intel SGX
SDK and C is expected to reduce the attack surface, and this
remains a direction for future work.
E. Trust Model in VDDPI Architecture
While VDDPI employs TEE to protect data processing, the
system architecture includes components that operate outside
the TEE boundary and require explicit trust assumptions, as
described in Section III-A. However, the system design manages
these trust dependencies to avoid single points of failure in
security-critical functions.
The AR’s distributed ledger infrastructure, CAs, static taint
analysis tools, and build systems operate in conventional com-
puting environments. Critically, the static taint analysis and build
processes are invoked through smart contracts executed across
multiple AR nodes. This distributed execution means that if any
individual node attempts to provide fraudulent analysis results
or tampered build outputs, the smart contract execution will
be interrupted due to consensus failure. Therefore, the core
veriﬁcation processes that determine data processing safety do
not rely on a single trusted point but rather on the collective
integrity of the distributed ledger network.
TEE protection is applied speciﬁcally to the most sensitive
operations—the actual processing of personal data—while the
veriﬁcation infrastructure leverages blockchain consensus to
eliminate single points of trust in the analysis pipeline. Data
providers retain ultimate control over provisioning decisions
based on these collectively veriﬁed results, ensuring that the
overall system maintains strong security properties despite the
hybrid trust model. This approach demonstrates how conﬁden-
tial computing can be effectively combined with distributed trust
mechanisms to achieve both data conﬁdentiality and veriﬁcation
integrity in decentralized data processing environments.
F . Practical Deployment Potential
Based on the experimental results presented in
Section VII-D, VDDPI introduces only a predictable amount of
memory overhead. However, the data processing time increases
linearly with the volume of data. Therefore, for use cases
requiring large-scale data processing and quick responses,
improving processing efﬁciency remains a key challenge. In
the assumed disaster evacuation support scenario, VDDPI
can provide timely assistance in small-scale facilities while
maintaining real-time performance. In contrast, when applied to
large-scale scenarios such as entire cities, data processing may
become a bottleneck, potentially causing delays in delivering
assistance. Nevertheless, the performance of VDDPI is largely
inﬂuenced by the underlying software conﬁguration. It is
therefore expected that replacing the software components used
in VDDPI could lead to further performance improvements.
Consequently, optimizing the implementation for service
integration and real-world deployment remains an important
direction for future work.
X. C
ONCLUSION
We proposed a data usage control method with data process-
ing veriﬁcation, but its practical implementation faces various
threats. In this paper, we present VDDPI, a decentralized data
processing infrastructure. VDDPI ensures data conﬁdentiality
by processing personal data in a TEE enclave and enforces
agreed usage conditions. It uses DLT for source code veri-
ﬁcation, allowing data providers to verify the usage control
and data processing before providing data, without relying
on a single point of failure. VDDPI allows data processing
apps implemented by data consumers to be veriﬁed within the
infrastructure, thus addressing not only scenarios where apps
are pre-implemented and ﬁxed, but also scenarios where there
is a need to establish a dynamic trust relationship between
data providers and consumers. VDDPI realizes a secure and
dependable infrastructure using TEE and blockchain technol-
ogy, and is expected to promote the utilization of personal
data.
We employed STRIDE to the assumed decentralized data
processing model to identify threats and veriﬁed that VDDPI
meets the requirements we derived. We also used ProV erif to
evaluate potential attacks and demonstrate VDDPI’s safety. A
