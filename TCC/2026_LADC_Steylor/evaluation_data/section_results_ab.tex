\subsection{A/B Comparison: Live Measurement of Both Environments}
\label{sec:ab-results}

To remove any inference from the comparison, we ran the full suite against both
deployments live and end to end: the compartmentalized system (Environment~B,
three containers \texttt{dnat-client}/\texttt{dnat-builder}/\texttt{dnat-executor})
and the centralized baseline (Environment~A, a single \texttt{dnat-baseline}
container that colocates the same logic). Because both environments share the same
Firecracker execution and build microVMs, we expect---and observe---that the
microVM-level properties and the operational cost are identical, while the
architectural variable surfaces only in the blast radius.

\textbf{The per-microVM guarantees are a constant.} Network-exfiltration
resistance (T1), filesystem containment (T1b), and persistence resistance (T3)
produce byte-for-byte equivalent evidence in A and B: the execution guest exposes
no usable network interface (all seven outbound channels fail at the syscall level
with \texttt{ENOSYS}/\emph{name resolution} errors), carries no control-plane
secret in its environment, sees no sibling tenant disk, and---verified through the
container's read-write layer after the campaign's runs---leaves behind no
Firecracker socket, no per-run \texttt{ext4} disk, and no working directory; only
the static, read-only rootfs template persists. Access control (T5) likewise holds
in both: an execution request issued without a prior \texttt{purchaseAccess} is
rejected with \emph{access denied} by the on-chain \texttt{hasAccessByIds} check in
A and in B alike, since that gate lives at the control plane, above the split.

\textbf{Compartmentalization adds no measurable cost.}
Table~\ref{tab:ab-performance} reports the operational cost on both paths. Across
three applications per environment, end-to-end execution latency is
indistinguishable between A and B (mean $\approx$26.8~s each), and a dependency-free
build (30.1 vs 30.2~s) and a build that pulls \texttt{requests} with its transitive
tree (38.2 vs 34.9~s) match within run-to-run variance, producing byte-identical
artifacts (16.0 and 19.6~MiB). The cost is paid by the microVM life cycle, which
both designs share; separating the planes does not add to it.

\textbf{Plane separation changes only the blast radius.} The single place where A
and B diverge is cross-plane reach (Table~\ref{tab:blast-radius}, now populated
from live inspection rather than configuration). In B, the executor and the builder
carry \emph{none} of the control-plane secrets
(\texttt{ASSET\_ENCRYPTION\_KEY}, \texttt{PRIVATE\_KEY}, the service URLs) in their
environment, and the sensitive stores (IPFS repository, wheel cache, executions
store) are absent from their namespace; the secrets live only in the control plane,
where they belong. In A, the very same secrets and stores sit in the single
namespace that also runs the execution logic. The supply-chain test (T2) inherits
this split: a compromised dependency's code executes, but in B it executes inside a
plane (build or execution) that holds neither secrets nor a route to them, whereas
in A the same code lands beside every sensitive asset. This is the paper's
comparative thesis---\emph{containment, not absolute security}---now demonstrated
with both environments measured, not one measured and one argued.
